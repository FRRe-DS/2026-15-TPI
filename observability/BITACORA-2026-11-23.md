# Bitácora — Equipo 2 — Grupo 15 — 23/11/2026

**Repositorio:** `FRRe-DS/2026-15-TPI`. **Rama:** `devops/observabilidad`.
Fecha en Argentina; algunos archivos de evidencia llevan 24/11 porque usan UTC.

## Tareas y decisiones

Se revisaron FastAPI, dependencias, casos de uso, Dockerfile, Compose y workflows
existentes. Se implementó OpenTelemetry opcional para HTTP y PostgreSQL con SDK
Python, exportación OTLP HTTP/protobuf, Collector Contrib y el mismo stack de
Grafana Cloud utilizado por el Grupo 02. Se creó e importó un dashboard separado
para el Grupo 15, con servicio `m3-conductores-grupo15`.

Se conservaron las tres métricas de negocio acordadas en la bitácora:

1. Conductores disponibles y habilitados: Gauge SQL agregado, cada 60 s, mediante
   vista y usuario de lectura sin acceso a tablas. Cuenta conductor `DISPONIBLE`
   y `APROBADA`, con vehículo activo propio `APROBADA`.
2. Tiempo de alta de conductor: histograma en segundos, desde recepción HTTP
   hasta retorno del caso de uso después de persistir y confirmar el commit.
3. Tiempo de actualización del estado operativo: histograma equivalente para
   cambios de estado/vehículo activo y aceptación de solicitud que pasa a ocupado.
   Se excluyen las actualizaciones de ubicación sola.

También se incorporaron solicitudes, latencia y errores HTTP, CPU y memoria RSS
del proceso Python. Se fijaron versiones del SDK y del Collector. Se eligió
instrumentar **psycopg** porque el instrumentador SQLAlchemy no admite la versión
2.1.6 usada por el repositorio; no se degradó el ORM ni se omitió su comprobación
de compatibilidad. La instrumentación no altera los casos de uso del dominio.

El proyecto Compose `m3-grupo15` tiene volumen y red propios y puertos alternativos
(API 18080, PostgreSQL 15432, Keycloak 18081, Redis loopback 16379, métricas 19464;
frontend opcional 13000), evitando conflictos con el Grupo 02.

## Resultados y alcance

En las pruebas sintéticas realizadas se observaron **Gauge en 1**, **una alta
exitosa** y **dos actualizaciones operativas exitosas** en el último proceso de la
API. Se obtuvieron POST **201** y PATCH **200**. Estos datos corresponden a esas
pruebas, no a carga ni a un inventario histórico. Los histogramas se reinician al
reiniciar el proceso. El Gauge en 1 corresponde al seed sintético; los conductores
nuevos quedaron pendientes y desconectados.

Grafana Cloud mostró las tres métricas y Tempo permitió consultar las trazas de
alta y actualización con spans SQL. El Gauge representa estado local de M3 y
aprobaciones persistidas: no recalcula vencimientos ni confirma un viaje de M4.
La prueba SQL de inclusión/exclusión y permisos se revirtió con rollback.

Ruff y las comprobaciones de formato/diff pasaron. La primera suite completa dio
1396 aprobadas. La suite final con psycopg dio **1394 aprobadas y 2 errores de
setup**, con **96,31 % de cobertura**, sin omisiones y excluyendo E2E explícitamente.
Los dos errores se mantienen pendientes; no se presentan como éxitos.

## Dificultades

Las pruebas `test_el_token_real_trae_los_ids_como_enteros` y
`test_el_token_de_servicio_solo_trae_el_rol_de_lectura`, del archivo
`backend/tests/infra/test_keycloak_claim.py`, fallaron antes de sus asserts porque
Testcontainers no encontró el puerto publicado de Keycloak. Se repitieron
aisladamente y el error persistió. Un diagnóstico posterior encontró el contenedor
ejecutándose, sin OOM y con puerto publicado: sugiere una carrera de descubrimiento
en Docker Desktop/Testcontainers. No se considera causa raíz definitivamente
confirmada. El Keycloak del Compose sí autenticó los smokes reales.
